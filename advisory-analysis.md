# Advisory Analysis

Based on the published logs from the OpenClaw Academy Security Advisories framework, a high-impact security advisory released in the August 26, 2026 update cycle details a critical vulnerability that allowed agents to both create and be in control of their own Gateway-hosted terminals regardless of the execution permissions. It also detailed a secondary vulnerability, where owner privileges could be claimed by public plugin ingress. Between these two vulnerabilities, the vulnerable components are the OpenClaw Gateway terminal subsystem and the session verification layer. The OpenClaw Gateway terminal subsystem is what handles how the application creates, opens, and routes interactive terminal window streams on the host machine, while the session verification layer handles how it checks a user's identity when text inputs pass through the gateway. The attacker-controlled input is a series of malicious text instructions or command strings, which are sent directly into an active terminal stream. The preconditions for these vulnerabilities require a live and running OpenClaw instance, where an agent session is active and has access to terminal skills or tools without manual user approval. The root cause for the terminal vulnerability is that the gateway accepted unverified requests from agents, letting them not only create their own terminals, but also control them, all without having to check the session permissions. The root cause for the verification vulnerability was that it trusted the sender's identity claim instead of verifying it directly. The impact from these vulnerabilities was the allowance of privilege escalation and bypassing policies. Because agents could open up their own terminals through the terminal vulnerability, they completely bypassed the safety measures set in place by the operator. For the verification vulnerability, there was a loss of trust regarding who is allowed to have a system identity. Because the system allowed a sender on a public channel to assert that it owned the conversation without verification, it could lead to the framework not being able to identify or differentiate between the trusted instructions from the actual user, or unverified instructions that were passed through by the untrusted source. This meant that any guest could falsely claim owner status, tricking the gateway into executing highly sensitive actions. The fix for these vulnerabilities involved enforcing newer, stricter tiles on how terminals open and how system identities are verified. First, only human users can create a terminal though the Control UI, agents are now completely blocked from opening terminals on their own. They can only list, read, resize, and close terminals that the user had already opened. Second, for the verification bug, the gateway stops taking the sender's word for who they are. Now, channel plugins must admit authenticated agent turns through their injected api.runtime.agent.runCommandFromIngress(options, runtime) capability. The host accepts owner authority only from the exact active, trusted plugin registered for options.messageChannel, and all other guest turns retain their non-owner identity. Finally, the public agentCommandFromIngress SDK helper never accepts a caller-supplied owner claim, making it impossible for an outside message to lie about being the owner. The automated regression tests check both fixes by reproducing the original privilege-escalation bugs. For the identity verification bug, the test acts as an untrusted public plugin ingress and tries to supply a fake owner privilege claim to reach owner-only tools. The test checks that the system strips away fake claims so unauthorized callers get access to no tools, while real owners using the trusted channel keep full access. For the terminal creation bug, the framework runs tests and live checks on a real Gateway with five interactive /bin/sh PTY terminals. The test verifies that agents cannot open shells on their own, and checks that terminal typing follows active safety settings. Prompt injection is helpful for the attack but has nothing to do with the actual bug. The real problem is a broken internal lock inside the gateway that failed to check user permissions on terminal streams.
